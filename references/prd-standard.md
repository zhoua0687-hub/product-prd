# PRD 标准：每一章写什么、怎么写

这份标准从一份真实的产品 PRD（抽奖工具）提炼而来，补上了交给 AI 时容易缺的几块。做完的样子见 `examples/抽奖工具-PRD.md`。

## 整体结构

```
# <产品名> PRD
> 交付深度：原型级 | 前端级
> 产品形态：App | 网站 | H5
> 目标市场：一句话
> 状态：草稿 | 已确认
> 标记：一行图例，说明两种标记的意思（模板里已经写好）

# 1. 背景与产品定位
## 1.1 项目背景
## 1.2 产品定位
## 1.3 核心价值
## 1.4 目标市场
## 1.5 范围和优先级

# 2. 用户流程和状态
## 2.1 用户流程图
## 2.2 状态字典

# 3. 产品前端页面描述
## 3.0 全局组件和通用规则
### 3.0.1 <全局组件名>
## 3.1 <页面名>            ← 标题下面紧跟这一页的大纲
### 3.1.1 <组件名>          ← 一个组件一张规格卡
## 3.2 <页面名>
### 3.2.1 <组件名>

# 4. 给 AI 的交付约束
## 4.1 平台和技术约束
## 4.2 后台配置总表
## 4.3 整页验收用例

# 附录
## 附录 A 待定问题清单
## 附录 B 决策记录
## 附录 C 埋点和衡量指标（可选）
## 附录 D 性能、兼容、无障碍、分享卡片（可选）
## 附录 E 术语和命名对照（可选）
```

节号就是每一节的身份证。别处提到某个组件时写它的节号，脚本靠节号核对。

设计相关的内容（品牌色、字体、对标截图、风格词）不写进这份 PRD，属于设计环节。

## 五个约定（脚本靠它们检查）

| 约定 | 写法 | 例子 |
|---|---|---|
| 大纲带节号 | 页面大纲第一层的每一项，末尾用括号写它的说明在哪一节 | `- 倒计时（3.1.3）` |
| 复用和全局 | 这一页用了别处定义过的组件，写「复用」或「全局」加节号 | `- 顶部导航（复用 3.1.1）`、`- 登录注册弹窗（全局 3.0.1）` |
| 引用别的组件 | 正文里提到别的组件、弹窗、页面，用 `【】` 括起来，名字和它的标题一字不差。这对括号只用来引用；文案里确实要出现它时，用反引号包起来 | `点击后弹出【登录注册弹窗】` |
| 待定 | 没定的地方写 `[待定 Q编号]`，后面跟默认假设，并登记到附录 A | `[待定 Q3] 默认假设：隐藏这个区域` |
| 建议 | 你补的、使用者还没确认的内容，行尾标 `〔建议〕`。规格卡里某一项整项都是你补的，在这一项的标签行末尾标一次就够；整张卡的细节都是你补的，在卡的开头写一句说明并标一次 | `头像加载失败时显示默认头像 〔建议〕`、`- **异常和边界**：〔建议〕` |

默认假设怎么取：文档或使用者已经有过说法的，取那个说法；有几种说法互相矛盾的，取最具体的那个，并在附录 A 里把几种说法都列出来；完全没提过的，取最简单的做法。你自己更推荐的方案写在附录 A 的「问题」一栏里，不要直接当成默认假设。

另外两条靠你自己守住，脚本查不全：

- **状态名一字不差。** 组件的「交互状态」表里提到全局状态时，用的名字必须和 2.2 状态字典完全一样。字典里叫「进行中」，这里就不能写「活动中」。
- **数字和条件写死。** 「3 秒」「5 个头像」「超过 2 行」，不写「几秒」「若干」「较长」。

## 第 1 章 · 背景与产品定位

### 1.1 项目背景

三句话讲清：现在有什么问题、现有的解法差在哪、我们要做什么。点名现有产品时写出它具体差在哪（「配置繁琐」「缺乏信任感」），不写「体验不好」。

### 1.2 产品定位

- **核心理念**：3 个词以内，后面每个组件的取舍都拿它来判断。
- **对标产品**：写清对标的是它的什么（界面风格、交互方式、某个功能），不要只写名字。
- **目标用户**：分端写。B 端是谁、用它干什么；C 端是谁、怎么来、要什么。

### 1.3 核心价值

2～4 条。每条的格式是「价值：靠什么实现」，比如「低门槛：支持 Google 和 Facebook 一键登录」。只有口号、没有实现手段的价值，后面落不到组件上。

### 1.4 目标市场

用一张表，一行一项：

| 项 | 要定什么 |
|---|---|
| 主市场和次市场 | 哪些国家或地区 |
| 界面语言 | 单语还是多语，默认哪种 |
| 时区和格式 | 时间按谁的时区显示；日期、数字、货币的格式 |
| 登录渠道 | 当地常用的登录方式 |
| 分享和任务渠道 | 当地常用的社交平台 |
| 支付渠道 | 涉及付费时才填 |
| 合规要求 | 隐私和 Cookie 同意、年龄限制、当地对这类业务的规定 |
| 设备和网络 | 主流机型和屏幕、网速 |

这一节最容易被跳过，后果也最直接：市场没定，界面语言就没定，AI 会中英文混着写文案。

### 1.5 范围和优先级

分三栏写：

- **这一版要做**：列到页面和组件。
- **这一版简化**：做，但用简单的办法（比如「邀请任务先模拟完成」），写清简化成什么样。
- **这一版不做**：明确列出来。不写的话，AI 会把「后续扩展」也顺手做了。

## 第 2 章 · 用户流程和状态

### 2.1 用户流程图

用 Mermaid 的 `flowchart`，代码块标注 `mermaid`。要求：

- 从用户进入开始，到每一种结局结束。
- 每个判断节点至少两条出路，都标上条件。
- 节点里写用户看得见的事（「显示等待开奖」），系统内部的动作单独成节点（「系统生成抽奖码」）。
- 流程多的产品可以分成几张图：一张总览，每条主线一张，各自是一个 `mermaid` 代码块，前面用一行粗体写图名。脚本会逐张检查。

### 2.2 状态字典

从流程图里把状态抽出来，列成表：

| 维度 | 状态名 | 判断条件 | 备注 |
|---|---|---|---|
| 活动 | 进行中 | 开始时间 ≤ 当前时间 < 开奖时间 | |
| 用户 | 未登录 | 没有登录态 | |

- 「维度」是状态属于谁：产品或活动、用户、某个业务对象。
- 只属于单个组件的状态（比如任务卡片的「验证中」）不放字典，写在那个组件的交互状态表里。
- 字典里的每个状态，第 3 章都要有组件接住，脚本会查。

## 第 3 章 · 产品前端页面描述

### 3.0 全局组件和通用规则

放两类东西：

- **全局组件**：在多个页面出现或被多个组件唤起的，比如登录注册弹窗、提示条、加载和空状态、通用的列表浮层。每个一张规格卡，节号 3.0.1、3.0.2……
- **通用规则**：对所有组件都成立的规矩，比如「可配置的内容一律从后台读取」「昵称一律脱敏显示」「时间一律按用户本地时区」。写成一个列表，放在 3.0 标题下面、3.0.1 之前。

### 3.N 页面和它的大纲

一个页面一节。标题下面先用一两句话说明这是什么页面、从哪进来，然后紧跟**页面结构（大纲）**：一个嵌套列表，从页面顶部写到底部。

```markdown
## 3.1 活动主页

活动进行中时用户看到的页面，从分享链接进入。

**页面结构（大纲）**

- 顶部导航（3.1.1）
  - 发起人信息
    - 头像
    - 昵称
  - 消息订阅按钮
- 轮播图区域（3.1.2）
  - 参与动态跑马灯
  - 轮播图
- 登录注册弹窗（全局 3.0.1）
```

规矩：

- 有底部导航或几个一级入口的产品，页面标题写成「入口名：页面名」，比如 `## 3.2 首页：鉴定报告页`。思维导图会按入口把页面归到一起，成为「入口 → 页面 → 组件」三层。用 `【】` 引用这个页面时可以只写冒号后面的页面名。
- 第 3 章开头放一张**页面清单**表（入口、页面、从哪进来），一眼看全有哪些页面。
- 顺序就是页面上从上到下的顺序。弹窗和浮层放在最后。
- 第一层的每一项都是一个组件，末尾带节号。第二层往下是它的组成部分，不带节号。
- 几个组件在页面上属于同一个区域时，可以先写一个不带节号的区域名，把这几个组件放在它下面一层。示例里的「参与抽奖 CTA 按钮区」就是这样，下面是按钮、社交证明、抽奖码三个组件。
- 组成部分本身也是一个独立组件时（比如任务列表里的任务卡片），同样带上节号，单独写一张规格卡。
- 一个页面有几种差别很大的形态（比如活动结束前后），分成两节来写，后一节里没变的组件写「复用」加节号，变了的地方集中写在一节「复用组件在本页的变化」里。
- 这个大纲就是思维导图的源文件。`prd.py mindmap` 直接读它。

### 3.N.M 组件规格卡

一个组件一节，固定七项，标签名不要改（脚本按标签找）。模板在 `templates/component-card.md`。

**目的**　一两句话：这个组件对用户或业务有什么用。写不出目的的组件，多半不该存在。

**验收标准**　一个列表。每条都要满足「拿着原型能当场判断对不对」：

- 写看得见的结果：「点击后弹出浏览器的授权请求，授权成功后按钮变为『已订阅』」。
- 写具体的数字和条件：「自动轮播，间隔 3 秒」「真实数据不足 10 条时，用预设的虚拟用户循环展示」。
- 不写各有各理解的词：流畅、清晰、显著、友好、美观、合理、适当。非写不可就量化。

**交互状态**　一张表，一行一个状态：

| 状态 | 什么时候出现 | 界面表现 | 用户操作后 |
|---|---|---|---|

- 「什么时候出现」引用状态字典时，状态名一字不差。
- 「界面表现」写样式和显示哪句文案（文案原文放在「文案」一项）。
- 「用户操作后」写点击、滑动之后发生什么；去别的组件用 `【】`。
- 至少想一遍这几种：默认、加载中、空、出错、不可用、已完成。不适用的不用写。

**后台配置项**　一张表。运营在后台能改的每一项都列出来；没有就写「无」。

| 配置项 | 类型 | 默认值 | 限制 | 说明 |
|---|---|---|---|---|

类型用这几种：文本、长文本、富文本、图片、图片列表、视频、链接、数字、开关、时间、单选、多选、列表。验收标准里只要出现「可配置」「从后台读取」，这里就必须有对应的一行。

**文案**　一张表，组件上出现的每一句话都列出来，包括按钮、提示、空状态、报错。

| 位置 | 文案 | 备注 |
|---|---|---|

界面语言按 1.4 目标市场。多语言时每种语言加一列。带变量的文案用花括号标出变量：`Joined by {N} people`。

**数据字段和示例数据**　组件要显示哪些数据，给一组像真的示例。

- 原型级：`字段 | 示例值` 两列就够。
- 前端级：`字段名 | 类型 | 来源 | 示例值`，来源写「后台配置」「接口」或「本地」。

示例数据要像真的：名字像这个市场的人名，数字有零有整。AI 做原型时会直接用它。

**异常和边界**　一个列表：数据为空、内容太长、图片加载失败、网络断开、重复点击、权限被拒绝时怎么办。使用者没提的，按 `references/component-patterns.md` 里的易漏点提出来问。

### 复用组件在本页的变化

写成一张表，不用七项：

| 组件 | 在本页的变化 |
|---|---|
| 倒计时（3.1.3） | 停止倒计时，定格在开奖时间，文案变为「已开奖」 |

这一节的标题里带「复用」两个字，脚本就不会按七项去查它。它的节号照常排（比如 3.2.1），但不出现在大纲里。复用的组件在本页完全没变化，也写一行「无变化」，表示这是确认过的，不是漏了。

## 第 4 章 · 给 AI 的交付约束

### 4.1 平台和技术约束

一张表。原型级和前端级要填的不一样，见 `references/ai-handoff.md`。

### 4.2 后台配置总表

不要手写。模板里留了一对标记，`prd.py config` 会把各组件的配置项汇总进去：

```
<!-- config:start -->
<!-- config:end -->
```

### 4.3 整页验收用例

按用户旅程写，通常 4～8 条。条数以这一条为准：流程图里的每一种结局，至少有一条用例走到。

```markdown
### 用例 1：新用户免费参与

- **前置条件**：活动进行中；用户未登录；活动配置为允许免费参与。
- **步骤**：
  1. 打开活动链接。
  2. 点击「参与抽奖」。
  3. 用 Google 登录。
- **期望结果**：
  - 登录成功后自动回到活动主页。
  - 抽奖码区域出现 1 个抽奖码。
```

## 附录

### 附录 A 待定问题清单（必填）

| 编号 | 位置 | 问题 | 默认假设 | 状态 |
|---|---|---|---|---|
| Q1 | 1.4 | 主市场是哪些国家 | 英语国家，界面用英语 | 待定 |

正文里每个 `[待定 Qn]` 都要在这里有一行。使用者定了之后：把正文改成定下来的内容、去掉标记，这里的状态改为「已定」，并在附录 B 记一笔。

### 附录 B 决策记录（必填）

| 日期 | 决定了什么 | 谁定的 |
|---|---|---|
| 2026-11-12 | 这一版不做多阶梯邀请奖励 | 使用者 |

「谁定的」只有两种：「使用者」或「采纳建议」。它让 PRD 留下一条线索：哪些是使用者自己的想法，哪些是采纳了调研建议。

### 附录 C、D、E（可选）

使用者要才写：

- **C 埋点和衡量指标**：这个产品看哪几个数字；每个组件上报哪些事件。
- **D 性能、兼容、无障碍、分享卡片**：首屏时间、浏览器范围、对比度和点击区域、分享到社交平台时显示的标题和图片。
- **E 术语和命名对照**：中文叫法、英文叫法、代码里的名字，一一对上。

## 写法上的规矩

- **使用者说过的话尽量原样保留。** 这份 PRD 是他的思路，不是你的作文。
- **一个事实只写一处。** 别处要用就引用节号，不要再抄一遍，否则改了一处忘了另一处。
- **先结论后解释。** 每一节第一句就是这一节定了什么。
- **不写空话。** 「提升用户体验」「打造极致产品」这类句子，对做原型的 AI 没有任何信息量。
