# 交给 AI：两档深度和任务书

PRD 的读者是做原型或前端的 AI。这份文件讲两件事：两档交付深度各要写到什么程度；任务书是什么、怎么用。

## 两档交付深度

阶段 0 问清楚是哪一档，写在 PRD 文件头的「交付深度」一行。

| 内容 | 原型级 | 前端级 |
|---|---|---|
| 第 1 章（背景、定位、价值、市场、范围） | 要 | 要 |
| 第 2 章（流程图、状态字典） | 要 | 要 |
| 第 3 章页面大纲和思维导图 | 要 | 要 |
| 规格卡：目的、验收标准、交互状态、文案 | 要 | 要 |
| 规格卡：后台配置项 | 要，列出配置项和类型 | 要，加默认值和限制 |
| 规格卡：数据 | 只要示例数据 | 字段名、类型、来源、示例值 |
| 规格卡：异常和边界 | 要，写主要的几种 | 要，写全 |
| 4.1 平台和技术约束 | 端、屏幕尺寸 | 加技术栈、兼容范围、配置怎么注入、接口约定 |
| 4.2 后台配置总表 | 要 | 要 |
| 4.3 整页验收用例 | 要 | 要 |
| 附录 C、D、E | 可选 | 建议写 D（性能和兼容）和 E（命名对照） |

原型级的目标是「看得见、点得动、状态都对」。前端级的目标是「拿去能接数据、能上线」。使用者说先做原型，就不要拿前端级的问题去问他。

以后要从原型级升到前端级，在同一份 PRD 上补，不用重写。

### 4.1 平台和技术约束怎么填

原型级：

| 项 | 例子 |
|---|---|
| 做在什么端 | 手机浏览器 H5，竖屏 |
| 屏幕尺寸 | 按 375 宽设计，320～430 宽不变形 |
| 要不要适配电脑 | 不要；电脑上居中显示手机宽度 |

前端级再加：

| 项 | 例子 |
|---|---|
| 技术栈 | 使用者指定的框架或平台 |
| 兼容范围 | 哪些系统版本、哪些浏览器、是否包括各应用的内置浏览器 |
| 配置怎么注入 | 后台配置以什么形式给到前端（比如一份 JSON） |
| 接口约定 | 组件里提到的每个动作对应哪个接口，入参出参的例子 |
| 多语言 | 文案是否抽成语言包 |

使用者没定的，照样写 `[待定]` 加默认假设。

## 任务书

`prd.py brief` 从 PRD 生成一份 `<产品名>-AI任务书.md`。交给 AI 时，PRD 和任务书一起给。

PRD 说的是「产品是什么样」。任务书说的是「你照着做的时候守哪些规矩、按什么顺序做、做完怎么自查」。

任务书里有：

1. **六条规矩。** 只做 PRD 列出的；状态按表做全；文案照抄；示例数据用 PRD 的；待定项按默认假设做并列出来；PRD 没写的选最简单的做法并说明。
2. **目标市场和范围。** 从 1.4 和 1.5 原样带过来，放在最前面，因为它们决定语言和做不做。
3. **状态字典。** 原样带过来。
4. **制作顺序。** 先全局组件，再按页面、按大纲从上到下。
5. **逐组件验收清单。** 每个组件的验收标准变成勾选框。
6. **整页验收用例。** 从 4.3 原样带过来。
7. **待定项和默认假设。** 从附录 A 原样带过来。
8. **交付时要附上什么。** 让 AI 交回一份自查结果。

任务书开头还会按交付深度写明这一次做的是什么：

- **原型级**：数据直接写在原型里，用 PRD 的示例数据；登录、验证、提交这类依赖后端的动作直接模拟成功，PRD 写了失败表现的另留一个演示入口；带一个只在原型里出现的**状态切换面板**，可以切到状态字典里的每一个状态。没有这个面板，「中奖已失效」这类靠点击走不到的状态就没法验收。
- **前端级**：技术栈、兼容范围、配置注入方式和接口约定以 4.1 为准；后台配置项全部从配置读取；接口没就绪时用示例数据做本地模拟。

任务书是脚本生成的，不要手改。PRD 改了就重新生成。

## 交给 AI 之前

1. `prd.py check <PRD.md> --final` 没有必须修的问题。
2. 附录 A 里剩下的待定项，使用者都看过默认假设，同意 AI 先按它做。
3. `〔建议〕` 都处理完了：确认的去掉标记，不要的删掉。
4. 思维导图和 PRD 第 3 章的大纲是同一版。

## AI 交回原型之后

拿任务书里的验收清单逐条对：

- 没做的组件、漏掉的状态：让它补。
- 它自己加的东西：对照 1.5 的范围，不在范围里的删掉。
- 它列出的「PRD 未规定」：这些就是 PRD 还要补的地方。回到对应的阶段问使用者，补进 PRD，重新生成任务书。

每做一轮，「PRD 未规定」应该越来越少。到某一轮它一条都列不出来，这份 PRD 就算写到位了。
