# **1. 背景与产品定位**
# 1.1 项目背景
在海外市场营销中，抽奖（Giveaway）是获取新用户和提升社群活跃度的低成本高效率手段。然而，目前市面上的抽奖工具要么过于复杂（如 Gleam.io 配置繁琐），要么缺乏信任感（用户担心黑箱操作）。我们是基于低代码平台设计一款**轻量级、配置灵活且具备高公信力**的抽奖工具模板html。
### 1.2 产品定位
* **核心理念**：极简参与、透明公正、社交裂变。
* **对标产品**：微信小程序“抽奖助手” (UI 风格与交互体验的 Benchmark)。
* **目标用户**：
  * **B端 (运营者)**：通过低代码后台快速搭建活动，所有的模块都是设置任务门槛（Twitter关注、Discord入群等）。
  * **C端 (参与者)**：通过 H5 页面极速参与，体验顺畅，结果可追溯。
### 1.3 核心价值
1. **低门槛**：支持 Google/FB 一键登录，无缝参与。
1. **高信任**：清晰的倒计时、赞助商背书、中奖名单公示。
1. **自增长**：通过任务机制（Tasks）引导用户分享和关注，实现流量裂变。

#### 3.1.1顶部导航组件说明
* 抽奖活动发起人信息
  * 目的：提升抽奖活动背书，建立信任感。
  * 验收标准：
  * 头像 (Avatar) 和 昵称 (Nickname) 都支持自定义配置，必须从后台配置读取。
* 消息订阅按钮
  * 目的：利用 PWA 或浏览器 Notification API 建立触达通道，触达告知用户开奖结果。
  * 验收标准：点击弹出原生浏览器授权请求，授权成功后按钮状态变更为“已订阅 (Subscribed)”。
* 汉堡菜单（个人中心）：
  * 目的：提供个人相关功能的折叠入口。
  * 验收标准：
    * 菜单项配置化：菜单 Icon、名称、跳转链接均可由低代码后台配置。
    * 默认包含：个人信息、参与记录（包含未开奖/已开奖/中奖记录）、常见问题 (FAQ)、联系客服。
#### 3.1.2轮播图banner组件区域说明
* **左上角：用户参与抽奖跑马灯**
  * **目的**：利用从众心理 (Social Proof)，营造活动火爆氛围。
  * **验收标准**：
    * **独立组件**：必须作为悬浮层覆盖在 Banner 左上角。
    * **数据回退策略**：若真实参与数据不足 10 条，前端需根据预设的虚拟用户库（昵称+头像）进行循环展示，确保不留白。
    * **样式**：半透明黑色背景，白色文字，单行垂直滚动。
* **Banner 图**
  * **验收标准**：
    * 支持多图轮播 (Carousel)。
    * 支持自动轮播（间隔 3s）及手势滑动切换。
    * 图片需做宽高比适配（建议 16:9），防止拉伸变形。
####
#### 3.1.3 倒计时组件区域
* **目的**：营造紧迫感 (FOMO)，明确告知用户活动的生命周期状态。
* **验收标准**：
  * **多状态展示**：
    * **未开始**：显示“距离活动开始还有：DD天 HH时 MM分 SS秒”。
    * **进行中**：显示“距离开奖/结束还有：DD天 HH时 MM分 SS秒”。
    * **已结束**：显示“活动已结束”或“已开奖”。
  * **时区适配**：**关键点**。前端必须获取用户本地浏览器时区，将后台配置的 UTC 时间转换为用户本地时间显示。
  * **临界点刷新**：根据抽奖活动结束视角配置，倒计时归零时，页面应自动触发状态刷新（无需用户手动刷新），同步更新 CTA 按钮状态。
####
#### 3.1.4 赞助商信息展示组件
* **目的**：通过展示知名品牌或 KOL 信息，增强公信力，“去体验”按钮，引导进入赞助商网站页面，给赞助商引流。
* **验收标准**：
  * **引流按钮自定义化**：“去体验”按钮，自行配置按钮文案和跳转URL。
  * **布局自适应**：支持配置 1 个或多个赞助商。单赞助商居中展示，多赞助商横向排列。
  * **内容限制**：Logo 需做 Object-fit: contain 处理；名称单行显示，超出显示省略号；简述限制 2 行，点击可展开或跳转。
#### 3.1.5 活动简述区域
* **目的**：介绍奖品价值、规则及卖点。
* **验收标准**：
  * **富文本渲染**：支持 HTML 渲染（加粗、链接、列表）。
  * **多媒体支持**：支持嵌入 YouTube/Vimeo 视频或上传 MP4（需配置封面图）。
  * **默认折叠**：若内容高度超过屏幕 50%，默认展示“展开更多 (Read More)”按钮，点击后平滑展开。

#### 3.1.6 参与抽奖 CTA 按钮与抽奖码区域 (核心交互)
* **目的**：用户转化的核心组件，根据状态机动态变化。
**A. 参与抽奖 CTA 按钮状态机**
1. **已结束-页面状态**：高亮主色，文案 "查看开奖结果"，跳转至开奖结果子页面。
1. **进行中 - 未登录**：
   1. **样式：**&#x9AD8;亮主色，文案 "参与抽奖"。
   * **交互：**&#x70B9;击触发“注册登录”组件弹窗，引导注册/登录。
1. **进行中 - 已登录 - 有可以参与抽奖的资格**：
   1. **样式：**&#x9AD8;亮主色，文案 "参与抽奖"，点击触发 `GetTicket` 接口。
   2. **判断是否任务列表有可参与任务：**
      * **根据是否有可参与任务进行判断处理**：按钮状态参与抽奖后，主按钮上方弹出小提示文案“做任务可获得更多抽奖码”；没有可参与任务则不弹出小提示文案“做任务可获得更多抽奖码”。
      * **交互**：点击后页面平滑滚动至 **3.1.7 任务列表区**，并伴随抖动动效提示用户。
1. **进行中 - 已登录 - 需做任务 (重点优化)**：
   * **逻辑**：若用户**有可参与任务**。
   * **样式**：高亮主色，文案 "参与抽奖"，按钮上方弹出小提示文案“做任务可获得更多抽奖码”。
   * **交互**：点击后页面平滑滚动至 **3.1.7 任务列表区**，并伴随抖动动效提示用户。
1. **已参与 - 等待开奖**：
   * **样式**：高亮主色，文案 "参与抽奖"。
   * **判断是否任务列表有任务：**
     * **交互**：点击后页面平滑滚动至 **3.1.7 任务列表区**，并伴随抖动动效提示用户。
     * **根据是否有可参与任务进行判断处理**：按钮状态参与抽奖后，主按钮上方弹出小提示文案“做任务可获得更多抽奖码”；没有可参与任务则不弹出小提示文案“做任务可获得更多抽奖码”。
1. **已结束 - 查看结果**：高亮主色，文案 "查看开奖结果"，跳转至开奖结果子页面。
&#x42;**. 参与者社交证明区域 (Social Proof Area)：**
* **位置**：紧贴 CTA 按钮下方（符合视觉动线）。
* **目的**：通过“已参与人数”和“真人头像”建立信任，利用从众心理促进转化。
* **验收标准**：
  * **UI 构成**：
    * **头像堆叠**：显示最近参与的 5 位用户的头像 (Avatar Stack)，头像间有部分重叠 (Overlapping)。
    * **文案**：显示 "Joined by **N** people" (已有 N 人参与)。支持数字缩写 (e.g., 1.2k)。
    * **入口**：右侧显示 "View All >" 或箭头图标。
  * **冷启动逻辑 (Cold Start)**：
    * 当 `Total_Participants < 10` 时
      * **可隐藏此区域**，避免显示“已有 2 人参与”造成的负面效应。
      * **可配置虚拟用户参与信息**，提升冷启动效果
  * **交互**：
    * 点击整个区域，以子页面形式弹出 **\[参与者列表浮层]**。
    * 浮层内无限滚动展示所有参与者的头像和昵称（需对昵称做脱敏处理，如 `J***n`），证明数据真实性。
**C. 抽奖码展示区域**
* **显示逻辑**：仅在用户状态为 `已获得抽奖码` 时显示。
* **UI 表现**：
  * **常规状态**：显著展示抽奖码（如：`TICKET-8821`）。
  * **交互**：一行展示四个已获得抽奖码，超过三行做收纳加载处理。
#### 3.1.7 获得更多抽奖码/任务列表区
* **目的**：通过“差异化奖励”和“动态排序”，激励用户完成更多任务以获取更多中奖机会（Tickets）。每个任务组件独立运行，互不干扰。
**A. 任务列表通用逻辑 (General Logic)**
* **动态排序机制 (Dynamic Sorting)**：
  * **逻辑**：可以配置任务列表的排序，其次始终将用户**可参与 (Actionable)** 的任务前置，已完成的任务后置沉底。
  * **顺序**：`[未完成任务] (按权重降序) > [已完成任务] (按完成时间倒序)`。
  * **价值**：确保用户第一眼看到的永远是“还能获取更多抽奖码”的机会，避免被已完成的死数据占据首屏。
* **奖励展示 (Reward Badge)**：
  * 每个任务卡片右侧必须显著标记该任务的价值。
  * **样式**：使用胶囊徽章 (Badge)，例如 `+1 Ticket` (普通任务) vs `+5 Tickets` (高价值任务)。
**B. 任务类型一：关注/访问类组件 (Social Actions)**
* **适用场景**：引导关注 YouTube 频道、Facebook 主页、加入 Discord 群组、访问官网等。
* **交互状态机**：
  1. **初始状态 (Pending)**：
     * 按钮文案： "Go" 或 "Follow"。
     * 样式：主色调高亮。
  2. **验证中 (Verifying)**：
     * 交互：用户点击跳转外链 -> 返回页面 -> 触发 API 验证。
     * 样式：按钮显示 Loading 转圈图标。
  3. **已完成 (Done)**：
     * 样式：整行卡片透明度降低 (Opacity 60%)，按钮变为绿色对勾图标 (Checkmark)。
     * 反馈：Toast 提示 "Success! You got +1 Ticket."。
**C. 任务类型二：邀请裂变类组件 (Referral Actions)**
* **适用场景**：病毒式传播，引导用户分享给好友。**此任务通常配置高额奖励 (e.g., +5 Tickets)**。
* **交互状态机**：
  1. **初始状态 (Actionable)**：
     * 文案： "Invite Friends (+5 Tickets)"。
     * 按钮： "Invite" 或 "Share"。
  2. **裂变动作 (Sharing)**：
     * 交互：点击调起原生分享面板 (Native Share Sheet) 或 复制专属邀请链接。
  3. **模拟完成/进度展示 (MVP Simulation)**：
     * *注：MVP 阶段简化逻辑，模拟完成状态。*
     * 逻辑：系统检测到邀请成功回调（或模拟回调）。
     * 样式：显示进度条 `1/1` 或 `3/3`。
     * 状态变更：任务卡片变为 **已完成 (Done)** 状态，自动沉底。
* **后续扩展预留**：支持“多阶梯邀请奖励”，例如邀请 1 人得 1 票，邀请 5 人得 10 票。
**D. 自动参与/奖励发放逻辑 (Auto-Trigger)**
* **独立结算**：每个任务完成后，**立即**单独发放对应的 Ticket 数量，并刷新页面顶部的“我的抽奖码”计数。
* **门槛判断**：若活动配置了“必做任务”，只有当所有标记为 \[Required] 的任务状态均为 Done 时，用户才算正式“Joined”，并获得基础参与资格

#### 3.2.1 底层页面复用组件状态说明
此部分描述原 3.1 首页组件在 `Status = Ended` 时的特殊表现。
* **倒计时组件区域**
  * **状态**：停止倒计时，文案进行变更。
    * 开奖时间->已开奖
  * **交互：**&#x52A8;态倒计时组件->定格在开奖的时间
* **CTA 按钮区组件**
  * **目的**：作为弹窗关闭后的“兜底入口”，防止用户迷路。
  * **验收标准**：
    * **文案**：变更为 "查看开奖结果" 。
    * **交互**：点击后不触发抽奖，而是重新唤起 \[中奖名单公示]（若名单较长建议在 CTA 下方展开或弹窗展示）。
###
#### 3.2.2 开奖结果揭晓组件说明 (Result Reveal Modal)
* **目的**：作为活动结束后的核心交互，承载用户的“高光时刻”或“结果告知”。
* **验收标准**：
  * **触发逻辑**：
    * 用户访问且 `当前时间 > 开奖时间`。
    * 系统接口返回用户参与结果后，**自动弹出**，无需用户点击。
    * 若用户手动关闭弹窗，刷新页面后**不再自动弹出**（通过 LocalStorage 记录），但可通过底层 CTA 按钮再次查看。
  * **中奖状态 (Winner View)**：
    * **视觉**：必须包含 Confetti（撒花）动效，持续 3-5 秒。
    * **内容**：清晰展示所中奖品的名称和图片，强化获得感。
  * **未中奖状态 (Loser View)**：
    * **视觉**：使用中性色或暖灰色。插画需传达“遗憾但感谢”的情绪，避免负面暗示。
    * **数据安抚**：文案需包含“共有 N 人参与”，通过展示巨大的分母来降低用户的挫败感。
#### 3.2.3 领奖交互区域说明 (Claim Interaction)
* **目的**：在中奖弹窗内完成信息收集闭环，避免跳转流失。
* **验收标准**：
  * **立即领奖按钮 (Claim Prize)**：
    * 点击后，弹窗内容**平滑切换**（Flip/Slide）为领奖表单。
    * **表单内容**：
      * **实物**：姓名、电话、地址（集成 Google Place Autocomplete）。
      * **虚拟**：展示兑换码及“一键复制”按钮。
  * **提交反馈**：
    * 提交成功后，弹窗切换为“等待发货”状态页。
    * 再次打开弹窗时，直接显示物流状态或卡密信息，不可重复提交。
###
#### 3.2.4 中奖失效遗憾视图说明 (Winner View - Expired) 
* **目的**：明确告知用户因逾期未操作导致奖品作废，并引导流量流转，避免用户以为系统出错。
* **验收标准**：
  * **视觉氛围**：
    * 使用**红色/警示色**标题（如 "Sorry, Deadline Missed"），但整体氛围保持克制，避免过度负面。
    * **失效印章**：在原本的中奖奖品图片上，必须覆盖一个倾斜的、半透明的 **"EXPIRED" (已失效)** 灰色印章或水印。
  * **文案说明**：
    * 必须明确展示：“领奖截止至 \[Date Time]，已超时，奖品已失效”。
  * **交互操作**：
    * **主按钮**：文案为 "Join Other Games" (免费参与更多抽奖)，点击跳转至活动列表页。
    * 此视图**不提供**“领奖”入口，也不显示“炫耀”按钮。
###
#### 3.2.5 导流交互区域说明 (Traffic Redirection)
* **目的**：转化未中奖流量，提升平台其他活动的曝光。
* **验收标准**：
  * **查看中奖名单 (See Winners)**：
    * 点击后**关闭当前弹窗**。
    * 页面自动滚动到底部（或通过 Toast 提示），展示全局中奖名单（需注意名单的隐私脱敏处理）。
